Work

Six systems, from problem to result

Each one started as a manual process someone was doing by hand. Internal names and data are left out; the shape of the problem and what it took to fix it are not.

01

Audit orchestration platform

30 to 3manual touchpoints per audit
Python, Flask, DynamoDB, Redshift, CloudWatch

Problem. Auditing a title meant hopping between fragmented tools, copying IDs by hand and waiting on email. Over 30 touchpoints and long cycle times, with no single view of what was in flight.

  • Title ingestion, allocation, prioritisation and a queue engine in one web app
  • Blind audit workflow with an automated comparison engine between reviewer and auditor
  • Automatic reassignment and email alerts when work stalls
  • DynamoDB for live state, nightly write to Redshift for history and dashboards
  • Super-user controls so rule changes need no code edits

Result. Used daily by 200+ people, saves about 18 analyst-hours a day and cut manual touchpoints from over 30 to 3.

02

Storefront compliance agent

Python, browser automation, cloud OCR, AWS

Problem. Checking that maturity ratings and content descriptors actually appear on screen meant a person walking the storefront title by title and pressing play. Slow, inconsistent, and easy to miss gaps.

  • An agent that navigates the storefront, discovers titles and simulates playback
  • Screenshot capture at the moment the rating overlay should appear
  • Cloud OCR turns the overlay into structured text evidence
  • Cross-check against the audit record of what the rating should be, pass or fail per title
  • Mismatches, missing signals and wrong ratings routed for root cause

Result. Replaced the manual walkthrough entirely. Auditors spend their time on exceptions, not navigation.

03

Risk-based sampling with a daily feedback loop

30%more critical defects caught, 11 workflows
SQL, Redshift, scheduled ETL

Problem. Quality sampling pulled items at random, so high-risk titles were under-checked and audit effort went to items that were fine. The thresholds were static and drifted away from the real defect pattern over time.

  • Deep dive on historical defects to find recurring risk patterns and error clusters
  • Sampling logic rewritten in SQL to weight the pool by those risk signals
  • Daily ETL ingests audit outcomes and re-tunes the signals, so detection follows the latest defect trend
  • Root cause on false positives and false negatives to keep the noise down

Result. 30% more critical defects detected across 11 workflows, with less audit noise, and a rule set that adjusts itself with minimal intervention.

04

Accuracy pipeline for automated rating decisions

SQL, Redshift, QuickSight

Problem. As rating and descriptor decisions moved from people to models, nobody could say precisely where the model and a human reviewer disagreed, or whether a disagreement was a model miss, a reviewer miss or a data gap.

  • Shadow-mode comparison: model output against the human decision for the same title
  • Defects classified by type so each one has an owner and a fix path
  • Anomaly categories for the cases that fit neither side
  • Dashboards that program owners and leadership read daily

Result. A single source of truth for model accuracy that replaced ad-hoc spot checks and gives a daily view of where to intervene.

05

Time and motion engine

Python, Flask, email routing

Problem. Teams knew a workflow was slow but not which step. Without step-level timing there was no way to set realistic weekly targets or pick what to automate first.

  • In-app step builder so each team defines its own workflow without code
  • Step-wise time capture and sequence tracking per run
  • Automatic handle-time calculation and workflow rollups
  • Bottleneck discovery with optimal versus achievable target modelling
  • Results routed to configured recipients per team

Result. Teams found automation candidates faster, standardised baselines and set weekly targets they could actually hit.

06

Review demand forecast for capacity planning

36months of catalog history behind the next-year baseline
SQL, Python, backtesting, HTML dashboard

Problem. Headcount planning for review teams ran on judgement. Catalog growth, territory launches and new rating regimes all change the volume, and none of it was in one model.

  • Three years of title and territory history rebuilt from catalog data
  • Separate models for live catalog volume and review events, each backtested before use
  • Break rules so a policy change does not get extrapolated as a trend
  • A leadership dashboard with the assumptions written next to the numbers

Result. A defensible next-year demand baseline that planning conversations now start from.
